# Reusable scene adapters

A memory palace binds meaning to an inspected landmark, not to arbitrary x/y/z values generated by a language model.

## Current scenes

- `reading-hall` / version `1.1.0`: original, texture-free procedural reading hall. Twelve distinctive landmarks. The same Three.js builder is used in the application and the portable export.
- `dust2` / version `dust2-vrchris-08f7ab9c-v4`: twelve measured landmarks from the recovered vrchris model. Curated worlds use a horizontal span of 100. Two isolated viewpoints were replaced by measured door landmarks; v4 orders the route geographically to avoid a large backtrack. Historical sixty-slot Dust2 saves retain their original 200-span route; they are not silently reassigned to the new twelve landmarks.

The original Dust2 GLB has 34 meshes, 34 materials, 34 embedded texture images and 9,294 triangles. Blender also contains default datablocks, so its total datablock counts are not the asset's material count.

## Contract

`src/lib/sceneRegistry.ts` owns stable scene IDs, versions and anchor metadata:

- Stable anchor ID and `L01`–`L60` storage ID, label, route order and zone
- Visible landmark features, material/color description and semantic tags
- Semantic affordances for creative inspiration only
- A ground-level approach, eye, look-at point and yaw/pitch
- A bounded cue volume with capacity and executable relation IDs
- Neighbors and relative landmarks
- Verification method and limitations, including an explicit unknown value for untested route reachability

`src/three/sceneAdapters.ts` owns `registerSceneGeometryAdapter` and `loadSceneWorld`. A new adapter supplies a validated definition and a geometry loader. Returned geometry must already use the definition's final Three.js Y-up coordinates. A `COLLISION` child can separate physical architecture from decorative details.

### Four executable relations

`ordered-row`, `orbit`, `frame`, and `rise` are implemented by the shared app/export cue renderer. `rise` means periodic up/down motion, accurately labeled “周期起伏”. Each cue executes its own operation in a disjoint slot inside the permitted volume. Slots are arranged left-to-right in the canonical viewing direction; they do not rotate as the user freely walks. Mixed relations do not override one another. Actual object extent, yaw rotation, pulse and rise envelopes are included in fitting.

Landmark language such as “cross through a window,” “split across two book pages,” or “grow from a real pot” is not an implemented placement relation. It must not be presented as actual rendered behavior. A creative mnemonic can mention an imagined association, clearly separated from the actual operation and from source facts.

## Adding a future environment

1. Recover and inspect the actual asset. Preserve ownership and licensing information.
2. Establish the coordinate transform and human-scale evidence. Use the exact transform in runtime and inspection tools.
3. Choose distinctive visible features. Prefer a small reliable set over a large guessed ring of points.
4. Measure ground-level approaches with body/head clearance. Check the full cue volume, not only its center. Current checks also use 27 eye-to-volume visibility samples per anchor and measured feature bounds for 21 object landmarks.
5. Create explicit semantic anchor IDs, legal cue volumes and scene-versioned approach views.
6. Register the adapter. Run `validateSceneDefinition` before registration.
7. Add an explicit portable packaging adapter. Registration alone does not make remote assets self-contained. Unknown export scenes must fail rather than fall back to Dust2.
8. Test the delivered runtime, route and target devices before describing them as browser-verified.

## Verification boundaries

The supplied inspection evidence includes real Blender GLB import, editable source scenes, geometry renders, Three.js capsule/ground checks and bounded cue-motion checks. Diagnostic cyan boxes show allowed cue volumes; they are not part of the user-facing world. Some inspection views use a labeled studio fill to make interior geometry readable.

These are not browser screenshots. Static visibility and settled capsules alone do not prove connectivity. The current curated routes additionally passed full actual-controller replay: one initial spawn and no inter-anchor or fall-recovery teleports. Dust2 v4 took about 80.75 seconds; the reading hall about 13.67 seconds at the test controller speed. An independent 90 Hz replay also passed. These checks apply to curated 12-anchor scenes, not historical 60-slot routes. Browser interaction, mobile appearance, performance, WebXR behavior and complete route traversal remain separate acceptance tasks.

## Camera framing

`anchorCamera.ts` keeps the verified eye fixed and adapts only the lens. It projects all eight cue-volume corners plus the landmark focus point into a camera with 10% horizontal and 12% vertical margins. The default vertical field of view is 70°, increasing to at most 110° for narrow displays. Very tall phone layouts can lose the requested margin even when the content still fits the canvas; the runtime reports this and offers landscape/text use. Mathematical framing is not a substitute for checking real UI overlays.

The editable Blender deliveries contain `L01`–`L12` approach empties, `CUE__...` volume empties, per-anchor cameras, a coordinate-conversion note and packed textures. Rendered cyan wire boxes are diagnostic aids, not final-world props.

## Visual-context package

`sceneVisualContext.ts` returns only manifests whose version, labels, eye/look-at and cue volumes still match the current scene. Each scene has twelve actual Blender approach images and one route overview. Public assets include SHA-256, byte length, dimensions, camera projection and attribution. These are optional reference images for a user-selected vision-capable model; no live model-vision capability is claimed or invoked by this package.

## Populated visibility stress check

Clock, atlas, mineral cabinet and elevated green-stack views were checked with three opaque boxes and three framed boxes from the actual shared renderer over 31 animation phases. Sampled landmark and key-feature pixels were not additionally occluded. The corresponding Blender stress views are labeled as diagnostics. This is a sampled clearance test, not proof of semantic memorability or browser rendering.

## Static rendering budget

The runtime can call `createReadingHallWorld({batchStatic:true})`. Only non-semantic static decoration is combined, within the existing collision/decor categories and with the same material objects. The result is 170 render meshes instead of 502 (66.1% fewer), with 25,238 triangles. Triangle positions, winding, normals, UVs and material signatures match at 1e-4 comparison precision; the optimized collision graph passes the same continuous route replay. All 158 landmark meshes remain independent.

The no-argument builder and Blender delivery preserve the full editable object structure. No FPS or device-performance result is claimed from these static counts. Batching never disposes shared materials/textures, and preserves any geometry still used by an unbatched landmark.

## Repeated preview cleanup

Each FpsWorld owns and releases its geometry/material/texture resources. Retired worlds, cue replacements, late asynchronous loads, model attachments, audio contexts and renderer lists are cleaned up; non-XR previews also release their WebGL context explicitly. Object-level tests verify idempotence and shared-resource safety. Actual repeated browser/GPU lifecycle behavior remains a separate runtime acceptance check.

## Physical entrance and boundary audit
Reading hall 1.1.0 closes the previously open floor-edge entrance with visible teal double doors, solid transom and jambs. Door leaves are 2.98m high across a 2.94m span; brass pull centers are 1.1m above the floor. Twenty actual-controller tests cover five outward starting positions, normal and 3x walking speed, and editable/batched collision geometry. All remain inside without fall-recovery teleport. The twelve-anchor continuous route still passes. The version changed because physical geometry changed; older plans require explicit rebinding.

A separate Dust2 main-component boundary audit filtered 36,459 unsupported outward samples through existing wall collisions and ran 71 plausible outward controller probes. None triggered fall recovery. This is a bounded sampled CPU audit, not proof of every trajectory or browser free-walk acceptance. No speculative invisible boundary walls were added.

## App attachment parity
The app uses the portable viewer's image-plane sizing and model-volume fitting for registered semantic anchors. The selected image occupies the cue center and faces the verified approach; an attached model is fitted within that same volume. Image, model and generated props are mutually prioritized in that order. Role and active-unit visibility remain controlled by MapPage; reference media is not loaded as a pre-answer cue.

Anchored images decode serially, preflight source headers, cap the displayed bitmap at2048px per side, and cache at most32MiB of RGBA data,16 entries and64MiB of compressed blob references. Source files remain unchanged. Clearing a locus hides its plane synchronously; generation checks dispose late decodes, and cache eviction preserves visible textures. These lifecycle/bounds tests use Three.js CPU objects and injected decoders; actual browser image decoding/rendering remains unverified.
